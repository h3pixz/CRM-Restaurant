# Техническое задание — Restaurant CRM

Сводное ТЗ по проекту. Источник правил разработки — `CLAUDE.md`,
живой чек-лист задач — `TASK.md`. При расхождении приоритет у `CLAUDE.md`.

## 1. Назначение

SPA для управления сетью ресторанов: сотрудники и смены, расчёт зарплат,
задачи, аналитика, отпуска и больничные, поиск ресторанов для доставки/самозаказа,
внутренний чат. Работа с данными — в реальном времени через Firebase Firestore.

## 2. Стек

| Слой | Технология |
| --- | --- |
| Сборка | Vite |
| Язык | TypeScript, `strict: true`, `noUncheckedIndexedAccess`, `any` запрещён |
| UI | React 19, Tailwind CSS v4, shadcn/ui (Radix UI), lucide-react |
| Роутинг | TanStack Router (code-based, типизированные параметры и search) |
| Асинхронное состояние | TanStack Query |
| Backend | Firebase Firestore |

> В формулировке ТЗ курса — «TanStack Query для работы с REST API (Firebase)».
> Фактически данные идут через Firebase SDK к Firestore; требование закрывается
> тем, что все запросы и мутации обёрнуты в TanStack Query.
| Чат | WebSocket `wss://ws.ifelse.io` |
| Карта | Leaflet + react-leaflet |

Дополнительные библиотеки (таблицы, графики, карты) допускаются, если
покрывают задачу без дублирования уже установленных.

## 3. Архитектура

Feature-based структура:

```
src/
├── app/              # роутер, провайдеры, QueryClient, навигация
├── components/       # переиспользуемые UI-компоненты (shadcn, layout)
├── features/         # фичи: api/, components/, types/, hooks/, data/, index.ts
├── lib/              # firebase, utils
├── routes/           # определения роутов
├── types/            # общие типы
└── utils/            # общие хелперы
```

Правила:

- Данные получаются и мутируются только через хуки TanStack Query в `features/*/api`,
  а не внутри презентационных компонентов.
- Firebase SDK изолирован в сервисных модулях; маппинг документов Firestore
  в доменные интерфейсы — отдельными функциями (`*-mapper.ts`).
- Каждая фича экспортирует публичный API через `index.ts`.
- Ошибки невалидных документов и конфигурации — с понятным текстом, без silent fail.

### Требования к экрану

- Состояния загрузки, ошибки и пустых данных — обязательны.
- Метрики/фильтры/поиск не ломают выборку; фильтрация типизирована через union-типы.
- Действия (View, Bonus и т.п.) — мутации TanStack Query с инвалидацией кэша.
- Вёрстка соответствует полученному макету: палитра, радиусы, шрифты Inter + Oswald.

## 5. Данные

### Коллекция `employees`

| Поле | Тип | Примечание |

Невалидный документ роняет запрос с понятной ошибкой.

### Рестораны

Сейчас — статические мок-данные (`features/restaurants/data`), структура
`Restaurant`: `id`, `name`, `city`, `cuisines`, `priceLevel`, `distanceFt`,
`images`, `location`, `labelSide`. Перевод на Firestore — отдельная задача.

### Конфигурация

Firebase инициализируется из `VITE_FIREBASE_*`; отсутствие переменных
роняет приложение на старте с понятным сообщением. `.env` не коммитится,
`.env.example` — коммитится.

## 6. WebSocket-чат

- Подключение к `wss://ws.ifelse.io` через нативный WebSocket.
- Состояния: connecting, connected, disconnected, error, reconnecting.
- Переподключение с backoff, ручное переподключение, отправка и история сообщений.
- UI чата соответствует остальному приложению; чат интегрируется в приложение,
  а не живёт отдельной страницей-демо.

## 8. Адаптивность под mobile

### Целевые устройства

- Основной сценарий — десктоп (CRM-админка, 1280px+).
- Mobile — поддержка планшета и телефона: 360–768px, без горизонтального
  скролла страницы и без обрезания контента.
- Отдельной мобильной версии/приложения нет: адаптируется та же SPA.

### Стратегия: два трека

1. **Во время разработки каждого экрана** — сразу закладывать адаптив.
   Новые экраны не должны добавлять мобильный долг: таблицы превращаются
   в карточки или получают локальный `overflow-x-auto`, фильтры — в sheet/drawer,
   sidebar — в выдвижное меню, карта на `/restaurants` — в переключаемую панель.
2. **Финальный проход** — когда все экраны из раздела 4 готовы, перед деплоем:
   аудит всех экранов на 360/390/768px, исправление накопленных проблем,
   проверка Lighthouse уже в мобильном профиле.

### Что нужно адаптировать

- Sidebar: на `< lg` скрывается в drawer с кнопкой-бургером в top bar.
- Top bar: заголовок не наезжает на иконки; уведомления и пользователь помещаются.
- Метрики Employees: сетка 1 → 2 → 3 колонки.
- Таблица Employees: карточный режим или горизонтальный скролл внутри контейнера.
- Фильтры и поиск: перенос в строку/шторку, тач-таргеты ≥ 44px.
- Restaurants: карта и список — вертикальный стек на мобиле (уже частично сделано
  через `lg:`-breakpoint), карточки в одну колонку.
- Чат: полноэкранная панель на мобиле вместо сайдбара.
- Диалоги: не выше `dvh`, внутренний скролл, безопасные отступы.

### Ответ на вопрос «когда адаптировать»

- **Не в конце одним куском и не сейчас отдельным этапом.**
- Каждый новый экран делается адаптивным сразу — иначе к релизу накопится
  переделка всех экранов разом.
- Полный проход по mobile — в разделе 6 `TASK.md` («Проверить responsive
  всех экранов»), после готовности всех разделов и до Lighthouse/деплоя.
- Адаптивность — критерий оценки из ТЗ, поэтому финальный проход обязателен
  и должен уложиться в дедлайн (2026-11-16).
- Уже готовые Employees и Restaurants проверяются в этом финальном проходе:
  Restaurants частично адаптирован (`lg:`), Employees — десктопный, требует доработки.
